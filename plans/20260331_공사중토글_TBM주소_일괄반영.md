# 공사중토글 ON 시 TBM 최신주소 일괄 반영 + 분기별 편집 제한

## 배경

| 항목 | 현황 |
|------|------|
| 전체 프로젝트 | 564개 |
| `actual_work_address` 채워진 건 | 45개 (8%) |
| TBM에 주소 있는 프로젝트 | 88개 |
| TBM 총 제출건 | 9,065건 |

- `projects.actual_work_address`는 대부분 비어 있음
- `tbm_submissions`에는 매일 `address` (+ `detail_address`)가 제출됨
- 기존 **공사중토글** 버튼은 본부별 분기 토글 설정만 ON/OFF
- **문제점**: 토글 ON 시 모든 분기(Q1~Q4)를 수정할 수 있어, 담당자가 아닌 사람이 다른 분기를 변경할 위험

## 목표

### 목표 1: 주소 일괄 반영
공사중토글 **ON** 시 → 해당 본부 소속 프로젝트들의 `actual_work_address`를 일괄 업데이트
- **1순위**: 최신 TBM 제출건(`status = 'submitted'`)의 `address` (+ `detail_address`)
- **2순위** (TBM 없는 프로젝트): 프로젝트 기본 주소 `site_address` + `site_address_detail`

### 목표 2: 분기별 편집 제한
공사중토글 **ON** 상태에서 → **현재 연도+분기만** 수정 가능, 다른 분기는 잠금
- 2026년 3월 → 2026Q1만 편집 가능, Q2/Q3/Q4는 읽기 전용
- 2026년 4월이 되면 → 2026Q2만 편집 가능

## 동작 설계

### 토글 ON 흐름

```
[공사중토글 클릭 (OFF→ON)]
  ├─ 1. 중복 실행 방지: isAddressUpdating 체크 → true면 무시
  ├─ 2. 기존 로직: 분기 토글 설정 ON (updateQuartersToggleSetting)
  ├─ 3. 추가 로직: TBM 주소 일괄 끌어오기 시작
  │     ├─ 로딩 표시 (토글 버튼에 스피너 + "주소 업데이트 중...")
  │     ├─ 해당 본부(managing_hq)의 프로젝트 목록 조회
  │     ├─ RPC 호출: bulk_update_actual_work_address(hq)
  │     ├─ projects.actual_work_address 일괄 UPDATE
  │     └─ 완료 시 로딩 해제 + 결과 토스트
  └─ 4. 화면 새로고침 (프로젝트 목록 재조회)
```

### 토글 OFF 흐름

```
[공사중토글 클릭 (ON→OFF)]
  └─ 기존 로직만 수행: 분기 토글 설정 OFF
     (주소는 건드리지 않음)
```

## 기술 구현 계획

### Phase 1: Supabase RPC 함수 작성 (DB 마이그레이션)

> **주의**: `projects` 테이블에는 현재 SELECT RLS 정책만 존재하고 UPDATE 정책이 없음.
> 클라이언트에서 직접 UPDATE하면 RLS에 의해 차단됨.
> → **SECURITY DEFINER** PostgreSQL 함수를 만들어 RPC로 호출하는 방식 채택.

```sql
-- database/migrations/add_bulk_update_address_function.sql

CREATE OR REPLACE FUNCTION bulk_update_actual_work_address(hq_division text)
RETURNS jsonb
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public
AS $$
DECLARE
  tbm_count integer;
  fallback_count integer;
BEGIN
  -- Step 1: TBM 주소가 있는 프로젝트 → 최신 TBM(submitted) 주소로 업데이트
  WITH latest_tbm AS (
    SELECT DISTINCT ON (t.project_id)
      t.project_id,
      CONCAT(t.address, ' ', COALESCE(t.detail_address, '')) as full_address
    FROM tbm_submissions t
    WHERE t.project_id IS NOT NULL
      AND t.address IS NOT NULL
      AND t.address != ''
      AND t.status = 'submitted'
    ORDER BY t.project_id, t.meeting_date DESC, t.submitted_at DESC
  )
  UPDATE projects p
  SET actual_work_address = lt.full_address
  FROM latest_tbm lt
  WHERE p.id = lt.project_id
    AND p.managing_hq = hq_division;

  GET DIAGNOSTICS tbm_count = ROW_COUNT;

  -- Step 2: TBM 주소가 없는 프로젝트 → 기본 주소(site_address)로 폴백
  UPDATE projects p
  SET actual_work_address = CONCAT(p.site_address, ' ', COALESCE(p.site_address_detail, ''))
  WHERE p.managing_hq = hq_division
    AND (p.actual_work_address IS NULL OR p.actual_work_address = '')
    AND p.site_address IS NOT NULL
    AND p.site_address != '';

  GET DIAGNOSTICS fallback_count = ROW_COUNT;

  RETURN jsonb_build_object(
    'tbm_count', tbm_count,
    'fallback_count', fallback_count,
    'total_count', tbm_count + fallback_count
  );
END;
$$;
```

**핵심 포인트:**
- **SECURITY DEFINER**: RLS를 우회하여 함수 소유자(서비스 역할) 권한으로 실행
- **`status = 'submitted'`**: 임시저장(draft) TBM은 제외, 제출 완료된 건만 사용
- **`managing_hq`**: projects 테이블의 본부 필드명 (⚠️ `headquarters` 아님)
- **`DISTINCT ON (project_id)`** + `ORDER BY meeting_date DESC, submitted_at DESC` → 프로젝트당 가장 최신 TBM 1건
- **반환값**: `{ tbm_count, fallback_count, total_count }` — UI에서 구분 표시 가능
- `detail_address` 컬럼이 tbm_submissions에 없을 경우 `COALESCE(t.detail_address, '')`가 빈 문자열 반환하여 안전

### Phase 2: 클라이언트 호출 함수 (`src/lib/projects.ts`)

```typescript
// 본부 소속 프로젝트들의 actual_work_address를 최신 TBM 주소로 일괄 업데이트
export async function bulkUpdateActualWorkAddress(hqDivision: string): Promise<{
  success: boolean
  tbmCount: number
  fallbackCount: number
  totalCount: number
  error?: string
}> {
  const { data, error } = await supabase
    .rpc('bulk_update_actual_work_address', { hq_division: hqDivision })

  if (error) {
    return { success: false, tbmCount: 0, fallbackCount: 0, totalCount: 0, error: error.message }
  }

  return {
    success: true,
    tbmCount: data.tbm_count,
    fallbackCount: data.fallback_count,
    totalCount: data.total_count,
  }
}
```

## 분기 편집 제한 상세

### 현재 동작 (문제)
```
공사중토글 ON 상태:
  Q1 [v]  Q2 [v]  Q3 [ ]  Q4 [ ]   ← 모든 분기 편집 가능
```

### 변경 후 동작 (2026년 3월 기준 = 2026Q1)
```
공사중토글 ON 상태:
  Q1 [v]  Q2 [—]  Q3 [—]  Q4 [—]   ← Q1만 편집 가능, 나머지 잠금
       ↑ 활성      ↑ disabled (회색)
```

### 분기 판정 기준
| 월 | 현재 분기 | 편집 가능 |
|----|----------|----------|
| 1~3월 | Q1 | q1만 |
| 4~6월 | Q2 | q2만 |
| 7~9월 | Q3 | q3만 |
| 10~12월 | Q4 | q4만 |

> **연도 주의**: 2027년 Q1에서 2026년 데이터의 Q1을 수정할 수 없도록, 데이터 연도와 현재 연도를 함께 비교해야 함.

## 고려사항

### 성능
- 한 본부에 약 100~150개 프로젝트 → SECURITY DEFINER 함수 내 단일 UPDATE 쿼리로 처리 (1~2초)
- 클라이언트에서 `supabase.rpc()` 1회 호출로 완료

### RLS 제약 및 해결
- `projects` 테이블에는 SELECT RLS 정책만 존재, UPDATE 정책 없음
- **해결**: `SECURITY DEFINER` PostgreSQL 함수로 RLS 우회
- 함수 내부에서 `managing_hq` 조건으로 범위 제한 → 보안 유지
- Supabase 웹 콘솔에서 마이그레이션 SQL 직접 실행 필요

### 데이터 안전성
- 기존 `actual_work_address` 값이 있어도 최신 TBM 주소로 덮어씀 (의도된 동작)
- **draft 상태 TBM 제외**: `status = 'submitted'`인 제출 완료 건만 사용
- TBM이 없는 프로젝트 → `site_address` + `site_address_detail`로 폴백
- `site_address`마저 없는 프로젝트 → 건드리지 않음
- OFF 시에는 주소를 삭제하지 않음 (한번 반영된 주소는 유지)

### 동시성 / 중복 실행 방지
- `isAddressUpdating` 상태로 버튼 disabled + 핸들러 early return
- 네트워크 지연으로 인한 연타 방지

### 주소 우선순위 정리

| 우선순위 | 조건 | 반영되는 주소 |
|---------|------|-------------|
| 1순위 | TBM 제출(`submitted`) 이력 있음 | 최신 TBM의 `address` (+ `detail_address`) |
| 2순위 | TBM 없음, `site_address` 있음 | `site_address` + `site_address_detail` |
| 미반영 | TBM 없음, `site_address`도 없음 | 변경 없음 |

### 엣지 케이스
- `project_id`가 NULL인 TBM → 스킵 (매칭 불가)
- 같은 날 여러 TBM 제출 → `submitted_at` 기준 최신 1건 사용
- `address`가 빈 문자열인 TBM → 스킵, 폴백으로 `site_address` 사용
- draft 상태 TBM → `status = 'submitted'` 필터로 제외
- `detail_address` 컬럼 부재 시 → `COALESCE`로 안전 처리
- 연도가 다른 데이터 편집 시도 → 현재 연도+분기만 허용
