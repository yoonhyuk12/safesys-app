# 프로젝트 병합 데이터 보존

## 목적과 범위

실제 DB와 최신 병합 SQL의 27개 직접 FK 이전 목록은 일치한다. 문제는 같은 날짜 작업일보와 같은 연월 품질 월간보고서의 source 행 삭제, projects의 일부 등록값 이전 누락, 월간보고서 충돌 안내 부재다.

1. 새 마이그레이션에서 보고서 충돌 시 병합 전체를 중단한다. 원본 보고서의 날짜·본문을 바꾸거나 삭제하지 않는다. 서로 다른 공정표가 양쪽에 있거나 공정표 이전 후 공사기간이 달라져도 중단한다. 두 프로젝트 행을 일정한 순서로 잠그고 DB에서 최종 충돌을 검사한다.
2. target 우선 원칙을 유지하며 비어 있는 공정표, 대표계약/나라장터 연계 묶음, CCTV, 상세주소, 알림앱 수신코드를 source로 보충한다. 대표계약과 나라장터 필드는 서로 다른 계약을 섞지 않도록 묶음으로 보충한다. 기존 주소·좌표는 일관된 묶음으로 유지한다.
3. API 서버에서 작업일보·품질 월간보고서 충돌을 조회한다. 미리보기 실패와 충돌 시 UI/POST 모두 차단한다. 미리보기 이후 경합은 DB가 최종 방어한다.
4. 운영 DB에 적용하기 전에는 새 안전 RPC를 사용할 수 없어 병합이 안전하게 실패하도록 버전이 명시된 RPC를 사용한다. 기존 RPC도 같은 안전 구현으로 갱신한다.
5. 격리된 PGlite에서 실제 SQL 회귀 테스트와 API/UI 관련 검증을 수행한다. 린트·타입체크·직접 diff 리뷰 후 로컬 커밋한다. 운영 DB 변경·실제 병합·빌드·푸시는 이 작업에서 실행하지 않는다.

## 조사와 재사용

- 기존 `database/20260831-1654_merge_projects_ai_usage_logs.sql`, `MergeProjectsModal.tsx`, `/api/projects/merge`를 확장한다.
- GitHub 코드 검색에서 병합/RAISE EXCEPTION/FOR UPDATE 패턴을 조사했다. 프로젝트 고유 FK·권한 구조이므로 외부 병합 코드를 도입하지 않는다.
- PostgreSQL 잠금 문서 https://www.postgresql.org/docs/current/explicit-locking.html.
- PGlite 테스트 DB 문서 https://pglite.dev/docs/about 및 https://pglite.dev/docs/api. npm 레지스트리를 확인해 개발 테스트용으로만 사용한다.
- feature-workflow가 참조한 superpowers 스킬은 현재 카탈로그/로컬 스킬 경로에서 찾지 못했다. 계획·테스트 우선·독립 리뷰 절차를 직접 적용한다.
