# 요청사항 게시판 구현 계획 (2026-08-19)

## 목표

SafeSys 사용자들이 시스템에 바라는 점을 올리고 서로 공감·논의할 수 있는 **전체 공용 게시판 1개**를 만든다.

## 확정 요구사항 (사용자 응답 기준)

| 항목 | 결정 |
|------|------|
| 범위 | 전체 공용 게시판 1개 (`/board`). `project_id` 없음 |
| 글 | 로그인 사용자 이름으로 작성·수정·삭제 |
| 댓글 | 작성·수정·삭제 |
| 투표 | 게시글·댓글 각각 추천/비추천 (사용자당 1표, 재클릭 시 취소) |
| 부가 기능 | **처리 상태 라벨만** (접수/검토중/반영완료/보류, 관리자만 변경) |
| 제외 | 분류(카테고리), 이미지 첨부, 검색·정렬 — 요청하지 않았으므로 만들지 않는다 |

## 아키텍처 결정

### 1. 데이터 계층은 RLS 직접 호출, 관리자만 service-role API

일반 사용자 동작(작성·수정·삭제·댓글·투표)은 클라이언트에서 `supabase`로 직접 호출하고 RLS가 권한을 강제한다 — 프로젝트의 기존 패턴(`src/lib/projects.ts`)과 같다.

관리자 권한은 **RLS로 판별할 수 없다.** 관리자 판정이 서버 전용 환경변수 `ADMIN_EMAILS`(`src/lib/admin-auth.ts`)에 있어 Postgres가 읽을 수 없기 때문이다. 따라서 관리자 전용 동작(상태 변경, 남의 글·댓글 삭제)만 `POST /api/board/moderate` 라우트에서 `requireAdmin()` + `supabaseAdmin`(service role)으로 처리한다. 이 방식은 관리자 목록을 DB에 복제하지 않아 드리프트가 없다.

부작용. `requireAdmin()`은 `amr: otp`를 요구하므로 관리자는 `/admin` 인증번호 로그인을 마친 세션에서만 조정할 수 있다. 게시판 UI는 `/api/admin/me`의 `isAdmin && otpVerified`일 때만 조정 버튼을 노출한다.

### 2. 상태(status) 변경은 트리거로 이중 방어

`board_posts`의 UPDATE RLS 정책은 작성자에게 열려 있으므로, 작성자가 직접 `status`를 바꾸는 것을 막아야 한다. `BEFORE UPDATE` 트리거에서 `auth.uid() IS NOT NULL`(= 일반 JWT 세션)인데 status가 바뀌면 예외를 던진다. service-role 호출은 `auth.uid()`가 NULL이라 통과한다.

### 3. 집계는 트리거 기반 비정규화

목록 화면에서 N+1 집계 쿼리를 피하려고 `upvotes` / `downvotes` / `comment_count`를 컬럼으로 두고 트리거로 유지한다. 클라이언트는 목록 1회 + 내 투표 1회 조회로 끝난다.

### 4. 작성자 FK는 `ON DELETE SET NULL`

계정이 삭제돼도 요청사항 본문은 남는 편이 낫다. `author_name` 스냅샷을 함께 저장해 표시 이름을 보존한다(`risk_assessments.author_name` 선례와 동일). `author_id`가 NULL이 되면 RLS상 아무도 수정·삭제할 수 없고 관리자 라우트로만 정리한다.

### 5. `merge_projects` 무관

게시판 테이블은 `projects`를 참조하지 않으므로 `merge_projects`의 FK 자식 테이블 수(26) 검증에 영향이 없다. 함수를 건드리지 않는다.
