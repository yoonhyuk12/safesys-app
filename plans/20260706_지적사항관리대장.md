# 지적사항 관리대장 기능 계획

작성일: 2026-07-06
근거 양식: [별지 6호 서식] 시정조치요구서 (지침 제22조), [별지 7호 서식] 현장점검 지적사항 조치결과 보고 (지침 제23조) — PDF 원본 제공

## 목표

프로젝트 상세 페이지 C(점검) 그룹에 **지적사항 관리대장**을 만든다. 본부 안전점검·정기점검(해빙기/우기/종합/특별)의 지적사항이 자동으로 1건씩 집계되고, 별지 6호 양식 형태로 직접 지적 등록도 가능하다. 조치(조치내용·조치 후 사진)는 원본 점검 화면에서든 관리대장에서든 등록할 수 있고(양방향 동기화), 건별로 별지 7호 조치결과 보고를 양식대로 다운로드한다.

## 양식 분석

**별지 6호 시정조치요구서** (직접 등록 폼의 필드 구성)
- 점검부서장 / 점검자 / 점검의 종류 / 점검일시 / 공사명(자동) / 점검내용 및 시정조치 요구사항

**별지 7호 현장점검 지적사항 조치결과 보고** (건별 다운로드, 1건 1페이지)
- 공사명 / 수급인 / 점검자(소속·직급·성명) / 점검일 / 조치완료일
- 지적부위
- 시정 전: 지적사항 + 사진 / 시정 후: 조치내용 + 사진
- 작성자: 현장대리인 (인) / 확인자: 감독원·건설사업관리기술자 (인)

## 설계 결정

1. **카드 위치**: A(조치) 그룹의 기존 "(자동) 지적사항 관리대장" 카드(준비중, `/issue-management`)를 **C(점검) 그룹으로 이동**, 제목 "지적사항 관리대장", `isPending` 제거. 라우트는 기존 `/project/[id]/issue-management` 재사용 (사용자 피드백 위치 = C 그룹 테두리).
2. **저장 모델 — 자동 집계는 저장하지 않음 (read-time aggregation + write-back)**
   - 본부 안전점검: `headquarters_inspections`의 issue_content1/2 → 지적 1~2건. 조치 = `action_photo_issueN` + `issueN_status` 갱신 (본부점검 페이지와 동일 컬럼 → 자동 동기화).
   - 정기점검: `safety_inspection_results` 실지적(사진 있거나 findings가 양호류 키워드 아님) → 조치 = `after_photo_url`('N/A'=해당없음) / `action_items`. 해빙기·우기·특별의 `additional_items` JSONB 지적(action ≠ '해당없음') → 배열 통째 갱신 (정기점검 관리대장 페이지와 동일 방식 → 자동 동기화).
   - 직접 등록: 새 테이블 `corrective_action_issues` 1행 = 지적 1건.
3. **새 테이블 `corrective_action_issues`** (`project_id UUID REFERENCES projects(id) ON DELETE CASCADE` + RLS)
   - 별지 6호: `inspection_department_head`, `inspector_name`, `inspection_type`(점검의 종류 TEXT), `inspection_date DATE`, `content`(점검내용 및 시정조치 요구사항), `location`(지적부위 — 별지 7호용)
   - 사진: `before_photo_url`, `after_photo_url` TEXT — Storage `inspection-photos` 버킷 `issue-direct` 폴더 (본부점검 페이지와 동일 버킷·업로드 패턴)
   - 조치: `action_content` TEXT, `action_date DATE`(조치완료일)
   - 서명(별지 7호): `contractor_signature`(현장대리인), `supervisor_signature`(감독원) base64 TEXT → **bulk-sign-targets.ts에 각각 contractor/supervisor로 등록** (CLAUDE.md 필수 규칙, selectColumns에 서명 제외)
   - `created_by`, `created_at`, `updated_at`
   - RLS: SELECT 전체 허용, INSERT/UPDATE/DELETE는 `auth.uid() = created_by` (inspection_visit_logs 동일 패턴). 단 조치 등록(UPDATE)은 타 역할도 필요하므로 UPDATE는 인증 사용자 허용으로 완화.
4. **마이그레이션 부수 작업** (CLAUDE.md 필수 규칙)
   - `merge_projects` 함수: UPDATE 목록에 `corrective_action_issues` 추가 + 개수 가드 20→21.
   - 프로젝트 삭제 라우트(`/api/projects/[id]/delete`): `before_photo_url`/`after_photo_url` Storage URL 수집 추가.
   - Supabase MCP 읽기 전용 → SQL 파일 작성 후 사용자가 SQL Editor에서 실행.
5. **관리대장 페이지** (`issue-management/page.tsx` 준비중 껍데기 교체)
   - 통합 테이블: 출처(본부/해빙기/우기/종합/특별/직접) · 점검일 · 점검자 · 지적부위(항목) · 지적사항 · 지적사진 · 조치내용 · 조치사진(업로드/해당없음/삭제) · 상태 배지(조치완료/조치대기) · 별지 7호 다운로드.
   - 정렬은 점검일 기준 (집계는 시행일 기준 — 프로젝트 규칙).
   - "지적 등록" 버튼 → 별지 6호 필드 모달. 미조치만 보기 필터 (본부점검 페이지 패턴).
   - 조치사진 업로드 핸들러는 출처별 write-back (2번 항목). 업로드 유틸·리사이즈는 본부점검 페이지의 로컬 패턴 답습.
6. **별지 7호 출력**: ExcelJS 1건 1시트 A4 세로, 사진 임베드(addImage) — 단속·점검방문일지와 동일 방침 (html2canvas PDF 미사용). `src/lib/excel/issue-action-report-export.ts`
   - 수급인: 정기점검 유래 = `safety_inspections.contractor` 스냅샷, 본부/직접 = 프로젝트 생성자 `user_profiles.company_name` (SafetyInspectionForm 패턴).
   - 조치완료일: 직접 등록건 = `action_date`, 소스 유래 = 공란.
   - 서명: 직접 등록건 = 새 테이블 서명 컬럼, 정기점검 유래 = `signatures` JSONB의 현장대리인/공사감독원, 본부 유래 = 공란. 서명은 성명 텍스트 위 겹침 렌더.
7. **권한**: 조치(사진·조치내용) 등록 = 전 역할 (본부점검 페이지와 동일). 직접 지적 등록·수정·삭제 = 발주청·감리단 (시정조치요구서 발행 주체).
8. **v1 제외**: 별지 6호 자체 다운로드(등록 폼이 양식 필드를 따르는 것으로 갈음), 카드 배지 카운트, 안전현황(/safe) 집계 연동.
