# TBM 일괄 텔레그램 발송 (AI 분석) 계획서

작성일 2026-07-17. 오케스트레이션(워커 2명 병렬)으로 진행.

## 공통 제약

- 모든 API는 로그인 세션의 `Authorization: Bearer <access_token>`을 검증한다.
- 요청 본문은 서버 경계에서 타입과 필수값을 검증하고, 인증된 사용자 범위의 프로젝트만 조회한다.
- 새 소스 파일 첫 줄에는 역할을 밝히는 한국어 주석을 둔다. `'use client'` 지시자가 있으면 바로 다음 줄에 둔다.
- 자동화 테스트 프레임워크를 새로 도입하지 않고 `npm run lint`, `npx tsc --noEmit`, 수동 시나리오로 검증한다.
- 두 워커는 공유 작업공간에서 지정 파일만 수정하며 커밋은 코디네이터가 검증 후 수행한다.

## 목적

`/tbm` 페이지에서 오늘 TBM 제출된 현장(작업없음 제외)을 소관사업별로 정리하고, 사용자의 검토 요청을 Gemini 3.1 Flash로 분석해 현장별 텔레그램 메시지를 생성·수정한 뒤, 발주청·시공사에게 일괄 발송한다.

## 사용자 플로우

1. TBM 데스크톱 헤더(복사 버튼 좌측)의 "AI 텔레그램" 버튼 클릭 → 모달 오픈.
2. 모달 상단에 대상 현장 목록(작업없음 제외, 소관사업별 정렬) 표시. 열림과 동시에 `/api/tbm-telegram/prepare`를 100건 단위로 순차 호출해 소관사업·텔레그램 수신 가능 여부 로드.
3. **소관사업 드롭다운("전체"+카테고리 목록)에서 사용자가 대상 사업을 선택** → 대상 표가 즉시 필터됨. 요청사항 입력(textarea, "어떤 부분에 대한 검토?") → "AI 분석 시작" 클릭 → 필터된 대상만 `/api/tbm-telegram/analyze` (Gemini 3.1 Flash).
4. 결과 표(스크롤): 체크박스(전체선택 포함), 소관사업, 현장명, 금일 작업·인원·장비, 분석 요약, 메시지(수정 가능 textarea).
5. 수신자 체크(발주청/시공사) → "발송" → `/api/tbm-telegram/send` → 행별 성공/실패 표시.

## API 계약

### POST /api/tbm-telegram/prepare
- req `{ items: [{ projectId: string|null, projectName: string }] }` (1~100건, UI는 전체 대상을 100건 단위로 나눠 원래 순서대로 결합)
- res `{ success: true, results: [{ projectId, projectName, projectCategory, hasClientTelegram, hasContractorTelegram }] }`
- projects 테이블에서 유효한 UUID의 id 일치 우선, 없으면 중복되지 않은 project_name 정확 일치(레거시 project_id NULL 대응). 응답 projectId는 해석된 canonical id 또는 null이며 category가 없으면 "미분류".

### POST /api/tbm-telegram/analyze
- req `{ userRequest: string, date: string, sites: [{ key, projectName, projectCategory, todayWork, personnel, equipment }] }` (1~50개 현장, userRequest 1~1000자, key는 중복 없는 UUID)
- res `{ success: true, results: [{ key, analysis, message }] }`
- 요청 key·날짜를 인증된 RLS 범위의 제출 완료 TBM과 대조하고, 작업없음 제외 및 전체 key 일치를 확인한 뒤 DB의 현장명·작업·인원·장비·소관사업으로 입력을 재구성한다.
- Gemini `gemini-3.1-flash`, responseMimeType application/json, 15현장 단위 청크 순차 호출. 결과는 key 전체 일치, analysis 최대 2000자, message 최대 1000자를 검증한다.

### POST /api/tbm-telegram/send
- req `{ requestId: UUID, items: [{ key: UUID, projectId: string|null, projectName: string, message: string }], recipients: { client: boolean, contractor: boolean } }` (1~30건, trim 후 message 1~1000자)
- res `{ success: true, results: [{ key, projectId, projectName, client: { attempted, ok, description? }|null, contractor: {...}|null }] }`
- 프로젝트 해석은 prepare와 동일 로직이며 같은 canonical 프로젝트의 중복 발송을 거부한다. 메시지는 HTML 이스케이프(& < >) 후 `sendTelegramMessage`를 사용한다.
- 사용자별 최근 10분 예약은 최대 2회다. 같은 requestId·payload의 완료/실패 결과는 저장 응답을 replay하고, 다른 payload는 409, 처리 중은 409, 속도 제한은 429로 외부 발송 전에 종료한다.

### DB 마이그레이션

- `database/20260717-0849_add_tbm_telegram_dispatches.sql`이 사용자별 requestId 예약, payload hash, pending/completed/failed 결과를 저장한다.
- 테이블 직접 권한은 회수하고 `SECURITY DEFINER` RPC만 authenticated에 허용한다. 사용자별 advisory transaction lock과 UNIQUE 제약으로 동시 예약을 직렬화한다.
- 완료 결과는 30건 이하, 실패 오류는 500자 이하이며 JSONB 이진·텍스트 크기는 각각 131072바이트 이하로 제한한다.

## 실행 작업

### Task 1: TBM 텔레그램 API

- 담당 파일은 `safesys-app/src/app/api/tbm-telegram/**`이다.
- `POST /api/tbm-telegram/prepare`는 1~100개의 `{ items: [{ projectId: string|null, projectName: string }] }`을 받아 `{ success: true, results: [{ projectId, projectName, projectCategory, hasClientTelegram, hasContractorTelegram }] }`을 반환한다. projectId는 canonical 해석 결과 또는 null이다.
- `POST /api/tbm-telegram/analyze`는 최대 50개의 `{ userRequest, date, sites: [{ key, projectName, projectCategory, todayWork, personnel, equipment }] }`을 받아 `{ success: true, results: [{ key, analysis, message }] }`을 반환한다.
- `POST /api/tbm-telegram/send`는 `{ requestId, items: [{ key, projectId, projectName, message }], recipients: { client, contractor } }`을 받아 `{ success: true, results: [{ key, projectId, projectName, client, contractor }] }`을 반환한다. 각 수신자 결과는 `{ attempted, ok, description? }|null`이다.
- 프로젝트 해석은 id 우선, 이름 정확 일치 폴백으로 처리하되 인증된 Supabase 클라이언트의 RLS 범위 안에서 조회한다.
- Gemini 분석은 요청 key 전체를 RLS 권위 데이터로 재조회한 뒤 `gemini-3.1-flash`, JSON 응답, 15현장 순차 청크를 사용하고 입력 현장 전체의 key가 유효하게 반환됐는지 검증한다.
- 텔레그램 발송은 빈 메시지를 거부하고 HTML 특수문자를 이스케이프하며, 개별 실패 후에도 다음 수신자·현장 발송을 계속한다. 예약 RPC를 통해 재발송과 사용자별 10분 2회 초과를 외부 호출 전에 차단한다.
- 관련 파일 기준 ESLint와 전체 `npx tsc --noEmit`을 실행해 결과를 보고한다.

### Task 2: TBM 텔레그램 모달과 헤더 연결

- 담당 파일은 `safesys-app/src/components/project/TBMTelegramBroadcastModal.tsx`, `safesys-app/src/components/project/TBMStatus.tsx`다.
- 모달을 열 때 로그인 세션 토큰을 포함해 prepare를 최대 100건씩 순차 호출하고, analyze/send에도 인증 헤더를 사용한다.
- 소관사업 드롭다운은 `전체`와 prepare 결과의 카테고리를 제공하며 선택 즉시 대상 표를 필터링한다. analyze 요청에는 필터된 대상만 포함한다.
- 결과 표의 전체선택·행선택·메시지 수정·수신자 선택·행별 발송 결과를 구현한다.
- `AI 텔레그램` 버튼은 데스크톱 헤더의 복사 버튼 바로 왼쪽에만 표시하고, 당일 `today_work !== '작업없음'` 레코드가 있을 때 활성화한다.
- 관련 파일 기준 ESLint와 전체 `npx tsc --noEmit`을 실행해 결과를 보고한다.

## 컨텍스트 노트

- 작업없음 판별은 `today_work === '작업없음'` (lib/tbm.ts와 동일 규칙).
- 소관사업 = projects.project_category. TBMRecord에는 없으므로 서버(prepare)에서 붙인다.
- 발주청/시공사 텔레그램 ID = projects.client_telegram_id / contractor_telegram_id (기존 sendProjectNotification 패턴).
- tbm_submissions 레거시 행은 project_id NULL → 이름 매칭 폴백 필수 (memory: project_tbm_legacy_null_project_id).
- Gemini 호출 패턴은 `src/app/api/ai/supervisor-summary/route.ts`의 work-daily-classify 분기 참조.
- 대상 레코드는 TBMStatus의 `allTbmRecords`(당일 전체 캐시)에서 selectedDate·작업없음 필터 적용.
- 텔레그램 기본 parse_mode가 HTML이므로 AI 생성 메시지의 & < > 는 발송 직전 이스케이프한다.
- 모바일 헤더(2313행 부근)에는 이번에 버튼을 넣지 않는다(요청 위치가 데스크톱 헤더). 필요 시 후속 작업.
- 발송 API 배포 전에 `database/20260717-0849_add_tbm_telegram_dispatches.sql`을 먼저 적용해야 한다. 이번 구현 세션에서는 실제 Supabase에 적용하지 않았다.
- 예약 직후 프로세스가 종료되면 pending이 유지되어 같은 requestId를 계속 차단한다. 불확실한 외부 발송의 중복을 막는 안전측 동작이며 운영 조회·수동 판정·보존기간 정책은 후속 범위다.
- 실제 Gemini·Telegram 호출과 DB 동시성 검증은 외부 부작용을 피하기 위해 실행하지 않았으며 배포 전 스테이징에서 확인한다.
