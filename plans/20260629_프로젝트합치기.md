# 프로젝트 합치기(병합) 기능 계획서

작성일: 2026-06-29

## 1. 목표와 동작

`/list`(목록 보기) 화면에서 두 프로젝트를 하나로 합친다.

- 우하단 플로팅 영역의 **공사중토글 버튼 왼쪽**에 "합치기" 버튼을 추가한다.
- 버튼을 누르면 모달이 열리고 두 개의 프로젝트 선택 줄이 나온다.
  - **1줄 = 대상(source)**: 삭제될 프로젝트. 이 프로젝트의 등록 내용이 빠져나간다.
  - **2줄 = 합산처(target)**: 내용을 받아 누적할 프로젝트. 그대로 유지된다.
- "합산" 누르면 로딩 스피너가 돌고, source의 모든 등록 내용(자식 행)이 target으로 옮겨진 뒤 source 프로젝트는 삭제된다.
- 완료 후 목록을 새로고침한다.

## 2. DB 조사 결과 (MCP로 확인)

### 2-1. 옮겨야 할 자식 테이블 — 15개

`projects(id)`를 `project_id`로 참조하는 테이블 전부. 모두 `ON DELETE CASCADE`이고, project_id 컬럼을 가진 테이블은 정확히 이 15개뿐이다(FK 없는 숨은 참조 없음). 2차 자식(worker_consents 등)은 `worker_id` 등을 참조하므로 부모가 옮겨가면 자동으로 따라온다 — 건드릴 필요 없음.

```
headquarters_inspections   manager_inspections        tbm_safety_inspections
heat_wave_checks           materials                  tbm_submissions
inspection_requests        new_worker_orientations    work_daily_reports
ptw_permits                project_shares             worker_registration_tokens
safe_document_inspections  safety_inspections         workers
```

병합 연산의 본질은 각 테이블에 대해 다음 한 줄이다.

```sql
UPDATE <table> SET project_id = <target> WHERE project_id = <source>;
```

### 2-2. 유니크 제약 충돌 위험 — 2곳 (단순 UPDATE 시 실패할 수 있음)

| 테이블 | 유니크 키 | 충돌 상황 |
| --- | --- | --- |
| `work_daily_reports` | `(project_id, report_date)` | source·target에 같은 날짜 작업일보가 둘 다 있으면 UPDATE 시 위반 |
| `project_shares` | `(project_id, shared_with)` | source·target이 같은 사용자에게 공유돼 있으면 위반 |

→ UPDATE 전에 "target에 이미 같은 키가 있는 source 행"을 먼저 삭제하는 방식으로 회피한다(아래 RPC 참조).

### 2-3. source 삭제 시 사라지는 projects 테이블 자체 데이터

자식 행이 아니라 `projects` 행 컬럼에 직접 담긴 값들은 source 삭제와 함께 사라진다(target은 자기 값 유지).

- `construction_schedule` (시공 예정공정표 JSONB) — **결정 필요**(아래 6번)
- `is_active`(분기별 공사중 JSONB), `total_budget`/`current_year_budget`, `supervisor_*`, `cctv_rtsp_url`, `business_card_pdf_url`(Storage), 좌표/주소 등 — source 고유 식별 정보이므로 폐기 타당.

## 3. 아키텍처

```
[합치기 버튼] → [병합 모달(source/target 선택)] → "합산"
      → POST /api/projects/merge  (service-role, 인증·권한 검증)
            → supabase.rpc('merge_projects', { p_source, p_target })  ← 단일 트랜잭션
                  → 15개 자식 UPDATE + 충돌 사전삭제 + source 삭제
      → 성공 시 getProjectsByUserBranch() 로 목록 새로고침
```

**왜 RPC(Postgres 함수)인가.** 15개 테이블 UPDATE + source 삭제가 **하나의 트랜잭션**으로 묶여야 한다. 중간 실패 시 데이터가 반쪽 상태로 남으면 안 된다. Supabase JS 클라이언트는 다중 테이블 트랜잭션을 지원하지 않으므로(순차 `.update()`는 비원자적), `plpgsql` 함수로 처리하고 API에서 RPC 1회 호출한다.

## 4. 백엔드 상세

### 4-1. Postgres 함수 (마이그레이션)

`database/`에 마이그레이션 파일로 작성한다(예: `database/16_merge_projects_function.sql`, 기존 번호 체계에 맞춰 조정). 적용 방식은 **결정 필요**(6번).

```sql
-- 두 프로젝트를 병합하는 함수: source의 자식 행을 모두 target으로 이전 후 source 삭제
create or replace function merge_projects(p_source uuid, p_target uuid)
returns jsonb
language plpgsql
security definer
set search_path = public
as $$
declare
  v_dropped_reports int;
  v_dropped_shares  int;
begin
  if p_source = p_target then
    raise exception '대상과 합산처가 같습니다';
  end if;
  if not exists (select 1 from projects where id = p_source) then
    raise exception 'source 프로젝트가 없습니다';
  end if;
  if not exists (select 1 from projects where id = p_target) then
    raise exception 'target 프로젝트가 없습니다';
  end if;

  -- 유니크 충돌 회피: target에 이미 같은 키가 있으면 source 행을 먼저 제거(target 우선).
  -- 이때 삭제된 source 행은 "합쳐지지 않고 폐기"되므로 건수를 집계해 반환·로깅한다.
  delete from work_daily_reports s
   where s.project_id = p_source
     and exists (select 1 from work_daily_reports t
                  where t.project_id = p_target and t.report_date = s.report_date);
  get diagnostics v_dropped_reports = row_count;
  delete from project_shares s
   where s.project_id = p_source
     and exists (select 1 from project_shares t
                  where t.project_id = p_target and t.shared_with = s.shared_with);
  get diagnostics v_dropped_shares = row_count;

  -- 15개 자식 테이블 project_id 이전
  update headquarters_inspections   set project_id = p_target where project_id = p_source;
  update heat_wave_checks           set project_id = p_target where project_id = p_source;
  update inspection_requests        set project_id = p_target where project_id = p_source;
  update manager_inspections        set project_id = p_target where project_id = p_source;
  update materials                  set project_id = p_target where project_id = p_source;
  update new_worker_orientations    set project_id = p_target where project_id = p_source;
  update project_shares             set project_id = p_target where project_id = p_source;
  update ptw_permits                set project_id = p_target where project_id = p_source;
  update safe_document_inspections  set project_id = p_target where project_id = p_source;
  update safety_inspections         set project_id = p_target where project_id = p_source;
  update tbm_safety_inspections     set project_id = p_target where project_id = p_source;
  update tbm_submissions            set project_id = p_target where project_id = p_source;
  update work_daily_reports         set project_id = p_target where project_id = p_source;
  update worker_registration_tokens set project_id = p_target where project_id = p_source;
  update workers                    set project_id = p_target where project_id = p_source;

  -- source 프로젝트 삭제 (자식은 이미 이전됨 → CASCADE로 지워질 자식 없음)
  delete from projects where id = p_source;

  -- 폐기된 충돌 행 건수 요약 반환 (사라진 데이터라 사후 재계산 불가 → 여기서 집계)
  return jsonb_build_object(
    'dropped_work_daily_reports', v_dropped_reports,
    'dropped_project_shares', v_dropped_shares
  );
end;
$$;

-- 클라이언트(anon·authenticated) 직접 호출 차단.
-- 주의: Postgres에서 함수 EXECUTE는 기본적으로 PUBLIC에 부여되므로 from public revoke 시
-- 모든 롤이 잃을 수 있다. 단, 이 프로젝트의 Supabase는 새 함수에 service_role EXECUTE를
-- "명시적으로" 부여(pg_default_acl 확인)하므로 revoke 후에도 service_role은 호출 가능하다.
-- 그 암묵적 전제에 기대지 않도록 service_role 권한을 명시적으로 재부여한다.
revoke execute on function merge_projects(uuid, uuid) from public, anon, authenticated;
grant  execute on function merge_projects(uuid, uuid) to service_role;
```

함수 본문은 암묵적으로 단일 트랜잭션에서 실행되어 원자성이 보장된다. `security definer` + `revoke`로 RLS 우회는 서버(service-role) 경로로만 가능하게 한다.

### 4-2. API 라우트 `POST /api/projects/merge/route.ts`

기존 `src/app/api/projects/[id]/delete/route.ts` 패턴을 그대로 따른다.

- Bearer 토큰으로 `supabaseAdmin.auth.getUser(token)` 인증
- `user_profiles.role === '발주청'` 로 권한 검증. 삭제 라우트는 `발주청 || created_by===user.id`(소유자도 허용)이지만, 병합은 비가역·파괴적이므로 **발주청만** 허용(삭제보다 엄격)
- body `{ sourceId, targetId }` UUID 검증, 둘이 다른지 확인, 두 프로젝트 존재 확인
- 지사 스코프: **API 별도 검증 없음**(6-5 확정). 발주청에게 보이는 프로젝트만 모달 목록에 뜨므로 선택 대상이 자연히 가시 범위로 제한됨 — 삭제 라우트와 동일 posture
- `supabaseAdmin.rpc('merge_projects', { p_source: sourceId, p_target: targetId })`
- RPC 반환 jsonb(폐기된 충돌 건수)를 받아 `{ success: true, dropped: {...} }` 형태로 반환

### 5-1. 합치기 버튼 추가 위치

`src/components/Dashboard.tsx`의 플로팅 컨테이너(2026-06-29 기준 약 4522행, 라인은 밀릴 수 있으니 내용으로 탐색):

```tsx
{viewMode === 'list' && (
  <div className="fixed bottom-6 right-6 flex flex-row gap-3 items-center">
    {/* 공사중토글 버튼 - canEditQuarters && userProfile?.hq_division 게이팅 */}
```

이 컨테이너는 `viewMode === 'list'`에서만 렌더된다. `flex-row`라 왼쪽→오른쪽 순서이므로, 공사중토글 **왼쪽**에 두려면 컨테이너의 **첫 자식**으로(=`canEditQuarters && userProfile?.hq_division` 블록 앞에) "합치기" 버튼을 넣는다. 버튼 표시 조건은 `userProfile?.role === '발주청'`(토글과 별개 게이팅).

스타일은 기존 토글 버튼과 통일(`rounded-full px-4 py-3 shadow-lg`), 색상만 구분(예: `bg-indigo-600`). 아이콘은 `lucide-react`의 `GitMerge` 또는 `Combine` 사용.

### 5-2. 병합 모달 (신규 컴포넌트)

`src/components/project/MergeProjectsModal.tsx` 신규 작성(상단에 한 줄 한국어 헤더 주석).

- props: 현재 `projects: Project[]`(Dashboard state, line 68), `onClose`, `onMerged`(새로고침 콜백)
- UI: 1줄 = 대상(source, **삭제될 쪽**) 선택, 2줄 = 합산처(target, **유지될 쪽**) 선택. 각 줄은 검색 가능한 select(프로젝트 수가 많으므로 사업명/지사 표시). 같은 프로젝트 동시 선택 방지.
- **확인 단계(필수, 선택 아님)**: source/target을 거꾸로 고르면 남기려던 프로젝트가 삭제되는 비가역 사고가 난다. 확인 단계에서 (a) "**삭제될 프로젝트: {source 사업명}**"을 빨간색으로 명시, (b) "**유지될 프로젝트: {target 사업명}**" 명시, (c) "되돌릴 수 없음" 경고를 반드시 노출한다.
- **겹치는 키 경고**: 합치기는 "합산"이라는 이름과 달리, 같은 날짜 작업일보·같은 공유대상은 합쳐지지 않고 source 것이 **폐기**된다(결정 6.2). 확인 단계에서 source·target에 겹치는 작업일보 날짜 수를 미리 조회해 "겹치는 작업일보 N건은 대상(합산처) 것만 남고 나머지는 삭제됨"을 보여준다. (미리 조회: 두 프로젝트의 `work_daily_reports.report_date` 교집합 count)
- "합산" 클릭 → 스피너(`Loader2`) → API 호출 → 성공 시 `onMerged()` 호출 후 닫기, 실패 시 에러 메시지. 성공 토스트에 RPC가 반환한 폐기 건수 표시.

### 5-3. 새로고침

병합 성공 후 Dashboard의 발주청 로딩 경로(`getProjectsByUserBranch(userProfile)` → `setProjects`, 2026-06-29 기준 약 1452행)를 재사용한다. 이 로직을 콜백으로 노출하거나 동일 호출을 모달 완료 핸들러에서 수행.

## 6. 결정 사항 (2026-06-29 확정)

1. **버튼 사용 권한** → **발주청 전체**. `role === '발주청'` 기준(버튼 노출·API 검증 동일). 삭제 API는 소유자(`created_by`)도 허용하지만 병합은 비가역이라 **발주청만** 허용(삭제보다 엄격).
2. **work_daily_reports 날짜 충돌** → **target 우선**. 합산처에 이미 있는 날짜는 유지하고 대상의 같은 날짜 행은 삭제. (RPC 4-1에 반영됨)
3. **construction_schedule(공정표) 등 프로젝트-레벨 데이터** → **폐기**. source 삭제와 함께 사라지고 target은 자기 값 유지. 별도 이전 로직 없음.
4. **마이그레이션 적용** → **`database/`에 SQL 파일 작성 → 사용자가 Supabase 콘솔에서 직접 실행.**
5. **지사 스코프** → **API 별도 검증 없음(2026-06-29 확정)**. 발주청은 가시 권한이 있는 프로젝트만 모달 목록(`getProjectsByUserBranch` 결과)에 뜨므로, 선택 가능한 대상이 곧 "보이는 프로젝트"로 자연히 제한된다. 별도 `branch_division` 검증을 API에 넣지 않는다(기존 삭제 라우트와 동일 posture). 참고: API는 모달이 거른 목록을 신뢰하므로 요청을 위조하면 안 보이는 프로젝트도 지정 가능하지만, 이는 기존 삭제 라우트와 동일 수준이라 회귀가 아니다.

## 7. Storage 영향 — 없음

모든 사진은 절대 public URL을 컬럼에 저장한다(예: `SafetyInspectionForm.tsx`가 `getPublicUrl()` 결과를 `photo_url`에 저장). project_id만 바꿔도 URL은 그대로 유효해 사진이 깨지지 않는다. 합치기는 Storage를 전혀 건드리지 않는다.

- 경미한 한계: `safety-inspection-photos` 버킷 파일은 물리적으로 옛 `{source_id}/` 폴더에 남는다. 표시는 정상이나, 훗날 target 삭제 시 삭제 라우트의 폴더 list(`list(target_id)`)가 이 파일을 못 찾아 정리에서 누락된다. source 프로젝트의 `business_card_pdf_url` 파일도 source 삭제 후 고아가 된다. 둘 다 기능 문제 아님 — 한계로 기록만.

## 9. 리스크

- **원자성**: RPC 단일 트랜잭션으로 해결(반쪽 병합 방지).
- **충돌**: 유니크 2곳을 사전 삭제로 회피(제약·인덱스 전수 조회로 그 2곳뿐임을 확인). 그 외 13개 테이블은 충돌 없음.
- **권한 우회**: `revoke execute` from public·anon·authenticated + `grant execute to service_role`로 서버 경로로만 호출.
- **되돌릴 수 없음 + source/target 혼동**: source 삭제는 복구 불가. 둘을 거꾸로 고르면 엉뚱한 프로젝트가 삭제되므로, 모달 **확인 단계 필수**(삭제/유지 프로젝트명 명시·"되돌릴 수 없음" 경고).
- **silent 데이터 폐기**: 겹치는 작업일보·공유는 합쳐지지 않고 source 것이 삭제됨 → 확인 단계에서 겹치는 건수 사전 노출, RPC가 폐기 건수 반환.
- **레거시 TBM(NULL project_id) 누락 — 2026-06-29 발견·수정**: 옛 `/tbm` 제출분(`tbm_submissions`)은 `project_id`가 NULL이고 TBM 현황이 `project_name+headquarters+branch` 텍스트로 매칭해 표시한다. v1 RPC는 `project_id`로만 이전해 이 행들을 누락 → source 삭제 시 화면에서 사라졌다(데이터는 보존, 표시만 누락). RPC에 "source 이름·본부·지사로 매칭되는 NULL project_id TBM도 target으로 이전"(`moved_legacy_tbm`) 추가로 수정. `tbm_safety_inspections`는 전건 project_id 보유라 무관.
