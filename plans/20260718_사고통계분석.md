# 사고 통계 분석 기능 계획

## 목표

- `/safe`의 12번째 카드로 `사고 통계 분석`을 추가한다.
- 기존 프로젝트를 선택해 실제 사고 이력을 등록·수정·삭제한다.
- 정기안전점검, 관리자점검, 본부불시점검의 일자와 핵심 내용을 사고 이력과 함께 조회한다.
- 점검 강도, 수행 완결성, 현장 위험 신호와 사고 발생의 통계적 연관성을 최근 12개월 기준으로 보여준다.

## 확정된 범위

- 분석 점검은 `safety_inspections`, `manager_inspections`, `headquarters_inspections` 3종만 사용한다.
- 아차사고는 기록하거나 분석하지 않는다.
- 점검 수준은 하나의 종합점수로 합치지 않고 다음 세 축으로 분리한다.
  - 점검 강도는 점검 건수, 프로젝트·월당 점검 수, 최근 점검 경과일로 표시한다.
  - 수행 완결성은 각 점검의 서명 완료 여부를 기준으로 표시한다.
  - 현장 위험 신호는 지적, 부적합, 미조치 건수와 비율로 표시한다.
- 모든 발주청 사용자는 자신의 조직 관할 프로젝트 사고와 분석을 조회할 수 있다.
- 사고 입력·수정·삭제는 본부급 이상 발주청 사용자만 가능하다.
  - 본사 또는 조직 관리자급은 전사 프로젝트를 관리한다.
  - 본부 사용자는 자신의 본부 프로젝트만 관리한다.
- 기본 분석 기간은 최근 12개월이다.
- 프로젝트-월을 관측 단위로 삼아 사고 전 30일·90일 점검 건수와 이후 사고 발생 여부를 비교한다.
- 근로자-일 또는 근로시간 분모는 1차 범위에서 사용하지 않는다.
- 아차사고와 피해자 개인정보는 저장하지 않는다.

## 화면 구조

1. `/safe` 카드 그리드의 법적이행확인 뒤에 `사고 통계 분석` 카드를 추가한다.
2. 루트 경로 `/safe/accident-analysis`와 지사 경로 `/safe/branch/[branch]/accident-analysis`를 지원한다.
3. 상세 화면 상단에 뒤로가기, 기간, 본부·지사·프로젝트, 사고유형·중대도 필터를 둔다.
4. 본부급 이상 사용자에게만 `사고 입력` 버튼과 사고행의 수정·삭제 기능을 표시한다.
5. KPI로 관측 프로젝트 수, 사고 건수, 부상자 수, 사망자 수, 총 점검 건수, 마지막 사고일을 표시한다.
6. 관계 분석은 사고 전 점검 건수 구간별 사고발생 프로젝트-월 비율을 막대와 표로 표시한다.
7. 월별 점검·사고 추이, 프로젝트별 요약표, 사고 이력표를 제공한다.
8. 사고 이력에서 사고 전 30일·90일 점검 수와 최근 점검 내용을 함께 확인한다.

## 사고 데이터 모델

신규 `project_accidents` 테이블을 사용한다. 오래된 `incident_reports` 초안은 현행 역할과 프로젝트 구조에 맞지 않아 재사용하지 않는다.

- `id`, `project_id`, `accident_at`.
- `severity`는 경상, 휴업, 중상, 사망 코드로 제한한다.
- `accident_type`, `location`, `work_description`, `description`.
- `cause`, `prevention_action`.
- `injured_count`, `fatal_count`, `lost_workdays`.
- `created_by`, `created_at`, `updated_at`.
- `project_id`는 `projects(id) ON DELETE CASCADE`를 사용한다.
- 모든 수치 입력은 0 이상으로 제한하고 필수 텍스트는 빈 문자열을 허용하지 않는다.

## 데이터베이스와 권한

- `project_accidents`에 RLS를 활성화한다.
- SELECT는 발주청 사용자의 조직 관할 프로젝트만 허용한다.
- INSERT, UPDATE, DELETE는 본부급 이상 발주청 사용자에게만 허용하고 프로젝트 관할을 함께 검증한다.
- INSERT의 `created_by`는 `auth.uid()`와 같아야 한다.
- 최신 `merge_projects` 함수에 사고행 `project_id` 이전을 추가하고 프로젝트 자식 테이블 개수 가드를 24개에서 25개로 갱신한다.
- 프로젝트 삭제 연관 건수 API의 안전·점검 범주에 사고 이력을 포함한다.
- `docs/database.md`의 현재 프로젝트 자식 테이블 개수를 25개로 갱신한다.

## 분석 정의

- 관측 기간의 각 프로젝트-월에 대해 해당 월의 사고 발생 여부와 사고 건수를 계산한다.
- 각 관측 월 시작 전 30일과 90일의 3종 점검 건수를 계산한다.
- 점검 건수 구간은 `0`, `1`, `2~3`, `4+`로 나눈다.
- 구간별 사고발생률은 `사고가 한 건 이상 발생한 프로젝트-월 / 해당 구간 프로젝트-월`로 계산한다.
- 월별 추이는 점검 건수와 사고 건수를 함께 표시한다.
- 프로젝트 요약은 점검 건수, 서명 완료율, 지적·미조치, 사고·부상·사망 건수를 표시한다.
- 사고 상세는 사고 전 30일·90일 점검 수, 가장 최근 점검 일자·유형·내용을 연결한다.
- 프로젝트-월 표본이 30개 미만이거나 사고 발생 프로젝트-월이 5개 미만이면 관계 수치에 `표본 부족`을 표시한다.
- 화면에 관찰자료의 연관성은 인과관계를 증명하지 않는다는 안내를 고정 표시한다.

## 구현 경계

- 신규 차트 의존성을 추가하지 않는다. Tailwind 막대, 표, 간단한 SVG 또는 CSS 표현을 사용한다.
- 준공 프로젝트의 과거 이력을 분석에서 제외하지 않는다.
- 기존 정기안전점검 집계 함수는 준공 프로젝트를 제외하므로 분석 전용 조회·정규화 함수를 별도로 둔다.
- 원본 점검 JSON을 사고행에 복사하지 않고 조회 시 공통 DTO로 정규화한다.
- Dashboard에는 카드, 경로 상태, 상세 뷰 연결만 추가하고 사고 폼 상태는 상세 뷰 내부에 둔다.

## 검증 기준

- 카드가 모바일 3열과 데스크톱 6열에서 12개로 정확히 배치된다.
- 루트·지사 경로, 새로고침, 뒤로가기가 유지된다.
- 지사급 발주청은 조회만 가능하고 입력·수정·삭제 UI와 DB 작업이 차단된다.
- 본부 사용자는 소속 본부 프로젝트만, 본사는 전사 프로젝트를 관리한다.
- 입력 검증, 빈 상태, 로딩 상태, 오류 상태가 사용자에게 명확히 표시된다.
- `npm run lint`, `npx tsc --noEmit`, `git diff --check`를 통과한다.
- 프로덕션 빌드는 사용자 동의 없이는 실행하지 않는다.
