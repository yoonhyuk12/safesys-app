# 프로젝트 삭제 시 Storage 사진 정리

## 배경

`deleteProject()`는 `projects` 행만 삭제하고, 관련 테이블 15개는 `ON DELETE CASCADE`로 함께 삭제된다. 그러나 **CASCADE는 DB 행만 지우고 Storage 버킷의 실제 사진 파일은 남긴다.** 그 결과 프로젝트 삭제 후에도 이미지 파일이 고아(orphan)로 버킷에 남고, 버킷이 모두 public이라 URL을 아는 사람은 계속 접근 가능하다.

## 목표

향후 프로젝트 삭제 시 관련 Storage 사진까지 함께 정리한다(collect-then-delete). 기존 고아 파일 일괄 정리는 범위 밖(별도 작업).

## 조사 결과

### 버킷 경로 구조 (제각각)

| 버킷 | 경로 패턴 | 프로젝트 식별 방법 |
|------|-----------|--------------------|
| heatwave-inspections | `{projectId}_{ts}_...` (평면) | 행의 URL 컬럼 |
| inspection-photos | `{점검ID}_{타입}_{ts}.jpg` (평면) | 행의 URL 컬럼 |
| tbm-photos | `signatures/...`, `education/...` (카테고리) | 행의 URL 컬럼 |
| worker-id-cards | `{UUID}/...` (폴더) | 행의 URL 컬럼 |
| safety-inspection-photos | `{projectId}/...` (폴더) | **폴더 list** |

→ URL이 모두 `https://....supabase.co/storage/v1/object/public/{버킷}/{경로}` 형태라 URL만 파싱하면 버킷·경로를 알 수 있다. `safety-inspection-photos`만 URL 컬럼이 없어 폴더 기반.

### 수집 대상 컬럼 (storage URL)

- `heat_wave_checks`: `photos`(jsonb 배열), `signature`
- `manager_inspections`: `inspection_photo`, `risk_assessment_photo`, `disaster_prevention_report_photo`
- `headquarters_inspections`: `site_photo_overview`, `site_photo_issue1/2`, `action_photo_issue1/2`
- `tbm_submissions`: `education_photo_url`, `signature_url`
- `workers`: `id_card_url`, `certificate_card_url`, `signature_url`

### 정리 불필요 (base64 인라인 → cascade로 함께 삭제)

`manager/hq/tbm_safety_inspections.signature`, `new_worker_orientations.manager_signature/mentor_signatures`, `safety_inspections.signatures`.

### 권한·보안

- `heatwave-inspections`는 Storage DELETE 정책이 없어 클라이언트로는 삭제 불가 → **service-role 필요**.
- service-role은 RLS를 우회하므로 `projects` DELETE RLS 보호가 사라진다. 따라서 API route에서 호출자 인증·권한을 직접 검증해야 한다.
- `projects` DELETE 권한 = `(user_profiles.role = '발주청') OR (projects.created_by = auth.uid())`.

## 구현

1. **신규 API route** `src/app/api/projects/[id]/delete/route.ts` (POST, service-role)
   - 호출자 토큰 검증 → 권한 확인(발주청 또는 소유자) → URL 수집 → 버킷별 삭제 → safety 폴더 삭제 → 프로젝트 삭제.
2. **`src/lib/projects.ts` `deleteProject()` 수정**
   - 세션 토큰을 실어 위 API route를 호출하도록 변경.

## 핵심 결정

- URL에서 버킷명을 파싱해 컬럼-버킷 매핑 하드코딩을 피한다. base64는 파서가 자동 스킵.
- `safety-inspection-photos`만 폴더(`{projectId}/`) 기반으로 list 후 삭제.
- 삭제 순서: Storage 먼저 → 프로젝트 행 나중(먼저 지우면 URL 복구 불가).
- Storage 삭제 실패는 로깅만 하고 프로젝트 삭제는 진행(부분 실패 허용).
