## Task 1 구현 판단 (Claude Opus)

- 제출 후 수정은 막는다. UPDATE 정책을 아예 만들지 않았다 — 서명은 제출 시점 점검 결과에 대한 것이라, 내용을 나중에 고칠 수 있으면 서명이 가리키는 대상이 달라진다. 정정은 삭제 후 재제출이다.
- 관할 판정을 새로 쓰지 않고 `projects` 조회 RLS에 얹었다. 정책 본문의 서브쿼리에도 RLS가 적용되므로 "그 현장을 볼 수 있는 사람만 그 현장의 점검을 본다"가 자동으로 성립한다. `is_project_owner`(리포에 없는 운영 함수)에 의존하지 않아 마이그레이션이 자족적이다.
- 답변 무결성은 `equipment_inspection_answers_valid` 함수 + CHECK로 DB에서 막는다. CHECK 제약은 서브쿼리를 담을 수 없어 함수가 필요하다. 화면 검증을 우회한 직접 호출로도 반쪽짜리 점검표가 남지 않는다.
- 서명 판정은 화면과 DB에서 PNG 매직·base64 문자·200자 이상으로 맞췄다. 캔버스의 빈 그림은 SignaturePad에서 별도로 거부한다.
- 병합은 마이그레이션 두 개로 나눴다. 테이블 생성(2245)과 `merge_projects` 갱신(2246)을 순서대로 실행해야 한다. 2245만 적용하면 FK 자식이 28개가 되어 병합이 개수 가드에 걸려 멈춘다.
- SQL 가드는 돌연변이 검사로 실효성을 확인했다 — created_by 검사 제거·SELECT 전면공개·answers CHECK 제거·서명 CHECK 제거·병합 UPDATE 줄 제거를 각각 넣었을 때 모두 테스트가 실패했다.
- 일괄서명 제외는 레지스트리에 넣지 않는 것으로 끝나므로, `bulk-sign-targets.ts`에 `equipment_daily_inspections`가 없음을 검증하는 회귀 테스트를 두었다.

## 독립 리뷰 반영 (Task 1 마감 전)

- 서명은 마지막 입력이다. 서명 뒤에 점검 결과·비고·기본사항 중 무엇이라도 고치면 서명을 지운다(`editEquipmentInspectionDraft`). 서명은 제출하는 내용에 대한 것이라, 내용이 바뀌면 그 내용에 다시 서명받아야 한다.
- 장비 교체 시 차량번호·기계번호도 함께 비운다. 그 번호는 이전 장비를 가리키는 식별자다.
- 서명 판정을 PNG dataURL로 좁혔다 — 형태만 맞고 내용이 깨진 base64는 HWPX에서 열리지 않는다. 화면과 DB CHECK가 같은 규칙(PNG 매직 `iVBORw0KGgo` + base64 문자 + 200자 이상)을 쓴다. 테스트도 실제 PNG 픽스처를 쓴다.
- 점검자 성명은 100자 이하 한 줄이다. 내보내기 경계값 계약과 맞췄고 UI `maxLength`·JS 검증·SQL CHECK 세 곳에 같은 값을 뒀다.
- 미점검을 해당없음으로 조용히 바꾸지 않는다. `buildEquipmentInspectionAnswers`는 결과가 비었으면 예외를 던지고, 미점검 판정은 값의 존재가 아니라 pass/fail/na 소속으로 한다.
- `answers`의 id·category·text·result는 SQL에서도 문자열로 강제한다. 내보내기가 문자열로 읽는 칸에 숫자·null이 오면 출력이 깨진다.
- 마이그레이션 미적용 상태를 빈 대장으로 표시하지 않는다. PGRST205·42P01을 "대장이 아직 개설되지 않았습니다"로 바꿔 알리며, 실행할 SQL 파일명은 사용자 화면에 노출하지 않는다.
- 복귀 경로에서 `returnUrl` 쿼리 지원을 뺐다. 외부 URL을 그대로 `router.push`하면 열린 리다이렉트가 된다. 이 화면은 프로젝트 상세로만 돌아간다.
- 저장 중에는 폼 입력·장비 선택·목록 선택·작성 닫기·삭제를 모두 잠근다. 늦게 도착한 성공 응답이 그사이 만든 새 초안을 닫아버리는 것을 막는다.
- 현장 조회 실패를 삼키지 않는다. 실패하면 재시도 버튼과 함께 알리고, 현장명이 확인되기 전에는 HWPX 다운로드를 잠근다 — 이름 없는 문서가 나가지 않게 한다.
- 마이그레이션 파일명은 작성 시각 기준으로 `20260914-2245`·`20260914-2246`으로 맞췄다.

## 최종 Advisor 검증

- 시공 C(점검) DOM에서 검사/검측 대장과 새 장비 일일점검 대장이 같은 그룹에 있고 하단 표기가 시공임을 확인했다. 서류철 클릭으로 새 페이지에 진입했다.
- 새 페이지 직접 URL 진입·새로고침 후 로그인 세션이 유지된다. getSession 초기화 완료와 onAuthStateChange로 이 페이지의 인증 상태를 판단한다.
- Orca 브라우저에서 장비 23종 선택, 굴착기 18항목 표시, 미점검·무서명·빈 캔버스 제출 차단, 서명 뒤 기본사항 변경 시 초기화를 확인했다.
- 해당 테이블의 fetch만 브라우저 메모리 응답으로 대체해 18항목 서명 제출·제출 목록·다운로드를 검증했다. 지연 POST 중 새 점검 및 장비 전환이 차단되고, 목록 다운로드로 현장명·굴착기·날짜가 포함된 22,417바이트 HWPX Blob이 생성됐다. 실제 DB 쓰기는 하지 않았다.
- 데스크톱 및 390×844 캡처(브라우저 확대율 때문에 CSS innerWidth 468)에서 가로 넘침 없이 표시됐다. QA 뒤 전체 탐색으로 fetch 대체를 제거하고 원래 테이블 미개설 상태로 복원했다.
- 최종 npx tsc --noEmit --incremental false 및 npm run lint exit 0, 관련 Node 테스트 89/89 통과. 기존 lint 경고는 남아 있고 새 기능 파일 경고는 없다. npm run test:equipment는 입력·출력 31개 테스트를 실행하도록 정리했고 재실행 통과했다.
- Orca의 실제 워커 터미널 3개는 모두 반환했다. 재사용 전 dispatch 기록은 retained로 남지만 resource=null이고 최종 owner dispatch는 released이며 회수 대상 워커는 0개다.
- SQL은 2245 테이블 생성, 2246 프로젝트 병합 갱신을 연속 실행하도록 안내한다. 실제 서비스 DB 반영은 사용자 작업으로 남긴다.

- 후속 요청. 사용자가 SQL 두 개 적용을 확인했다. 새 패키지나 생성 로직 없이 기존 page의 조건부 렌더링을 조정한다. 추가 테스트 코드를 만들기보다 실제 브라우저로 빈 목록/기록 있는 목록/장비 선택/닫기 상태를 검증한다.

- 후속 UI 검증 완료. 실제 빈 대장에서는 제출 목록 한 패널과 표 중앙 버튼 1개, 목록 너비 1241/컨테이너 1243px를 확인했다. 점검하기에서 장비 23종 표시 → 굴착기 선택 후 선택 버튼 0개와 점검표 18항목 → 닫기 시 목록만 → 다시 열기 시 23종 복원을 확인했다. 읽기 전용 모의 기록으로 목록 상단 버튼 1개 및 상세 열기를 확인하고 전체 탐색으로 모의를 제거했다.
