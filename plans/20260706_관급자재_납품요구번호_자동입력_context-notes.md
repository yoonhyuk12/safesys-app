# 컨텍스트 노트 — 관급자재 납품요구번호 자동입력

## 2026-07-06 결정 사항

- **입력 방식 선택 위치는 "자재 등록 모달"** — 사용자가 "수불부 추가할 때 직접 입력/납품요구번호 선택" 요청. 내역(행) 추가 모달은 일별 수불 이벤트 입력이라 납품요구 개념과 맞지 않아 제외. 자재 등록 시점에 자재+품목별 발주 행을 한 번에 생성하는 게 자연스러움.
- **유효 수량 = incdecQty 합산** — 실데이터(R25TB00824197)에서 차수00 incdecQty=194.05(최초), 차수01 incdecQty=-194.05(취소)로 확인. prdctQty는 차수별 자체 수량이라 합산 대상이 아님. 품목 메타(규격·단가·기한)는 최신 차수 행 기준.
- **DB 스키마 변경 없이 구현** — dlvr_req_no 저장은 후속 단계로 미룸. Supabase MCP가 읽기전용이라 마이그레이션은 사용자 콘솔 적용이 필요해 이번 UI 작업을 막지 않도록 분리.
- **자재명/단위는 첫 선택 품목 기준** — 납품요구 하나에 품목 여러 개면 세부품명이 대개 동일(레미콘 규격들 등). 다르면 사용자가 등록 후 자재명 수정 가능.
- **수량 0(전량 취소) 품목은 기본 체크 해제** — 목록에는 표시하되 기본 선택에서 제외.
- **API 키 이름 확정: `DATA_GO_KR_API_KEY`** — 계정당 1키 구조 확인(사용자가 재발급 시도했으나 동일 키 발급됨). Vercel에도 같은 이름으로 등록됨.
- 엔드포인트 경로가 차세대 나라장터로 바뀜(`/1230000/at/...`). 구버전 경로(`/1230000/ShoppingMallPrdctInfoService`)는 500 반환. 명세는 data.go.kr 15129471 페이지 HTML 내 `var swaggerJson`에 내장.

## 2026-07-06 추가 결정 — 계약수량 변경 처리 방식

- **발주량 변경은 ± 증감 행 추가로 처리** (사용자 결정). 원 발주 행을 수정하지 않고 변경분을 새 행의 발주량에 +50 / -30 식으로 기록 — 종이 수불부 관행 및 조달청 차수 증감 모델과 일치. DB 컬럼 추가 없이 동작.
- 이를 위해 `calcEffectiveOrderQty()` 도입 — 유효 발주량 = 첫 행 발주량 + 증감 행 합산. **증감 행 판별: 발주량만 입력되고 반입·합격·불출 수량이 전부 빈 행.** (일반 수불 행은 잔여발주량이 발주량 칸에 자동 저장되므로 단순 합산 불가 — 첫 행 기준 + 증감 행 방식이어야 기존 데이터와 호환)
- 증감 행 입력 시 주의: 행 추가 모달이 출고량·날짜를 자동 채우므로 반입/합격/출고 칸은 비워야 증감 행으로 인식됨.
- 이후 자동 동기화 기능을 만들 때도 같은 패턴(증감 행 자동 추가)으로 구현하면 일관됨.

## 2026-07-06 연계 버튼 구현 결정

- **연계와 동기화는 같은 모달** — 미연계 자재는 번호 입력부터, 연계된 자재는 저장된 번호로 자동 조회. 버튼 색으로 상태 구분(연계됨 = 파란색).
- **매칭 기본값 우선순위**: ① 행에 저장된 품목순번(dlvrReqPrdctSno) ② 규격 문자열 완전 일치 ③ 품목·규격이 각 1개면 자동 페어링. 그 외는 사람이 select로 선택.
- **발주량 차이 처리**: 조달청 기준 보정(증감 행 추가)이 기본 체크. 체크 해제 = 원장 유지(연결만). 합격 누계 > 조달청 수량(초과 반입)이면 체크박스 자체를 숨기고 경고만 — 자동 보정 금지.
- 연계 정보 저장 위치: 규격의 **첫 행**에 dlvr_req_no + prdct_sno 업데이트, 보정 증감 행과 신규 규격 행에도 동일 저장. materials에는 번호 + synced_at.
- 적용 후 `loadData()` 전체 재로딩 — 부분 상태 갱신보다 단순·정확 우선.
- 같은 규격에 품목 2개 매핑은 적용 시점에 차단(alert).
