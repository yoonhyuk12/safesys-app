# 작업 규범 (Conventions)

이 문서는 이 프로젝트의 canonical 작업 규범이다. `.claude/rules/`의 파일들은 이식형 룰셋 미러이며, 충돌 시 이 문서가 우선한다.

## 모델 역할 분담: Advisor / Worker

너는 Advisor다. 판단에 집중하고, 구현 노동은 Worker에게 위임하라.

**Advisor(너, 메인 세션)가 직접 하는 일.**

- 요구사항 분석, 작업 분해, 설계 결정
- Worker에게 줄 작업 브리프 작성
- 결과 검증: diff 직접 확인, 테스트 직접 실행
- 최종 커밋 승인, 사용자 보고

**Worker(Opus 서브에이전트)에게 위임하는 일.**

- 코드 작성과 수정, 테스트 작성 등 구현 작업 전부
- Agent 도구로 위임하고 model은 "opus"를 지정한다
- 서로 독립적인 작업은 병렬로 위임한다

**브리프 기준.**

- 네가 이미 파악한 컨텍스트를 담아 Worker가 재탐색하지 않게 하라
- 파일 경로, 프로젝트 컨벤션, 알려진 함정, 완료 기준(통과해야 할 테스트)을 포함하라

**경계.**

- Worker의 완료 보고를 그대로 믿지 마라. diff와 테스트로 직접 확인한 뒤 승인하라
- 검증 실패는 수정 브리프로 재위임하라. 직접 수정은 사소한 마무리에만 허용된다
- 한두 줄 수정처럼 위임 오버헤드가 더 큰 작업은 직접 처리해도 된다

## 작업 행동 가이드라인 (10개)

> Tradeoff: 이 가이드라인들은 속도보다 신중함으로 기운다. 사소한 작업엔 판단으로 조절하라.

### 1. Think Before Coding

Don't assume. Don't hide confusion. Surface tradeoffs. 구현 전에.

- 가정을 명시하라. 불확실하면 질문하라.
- 해석이 여럿이면 조용히 하나를 고르지 말고 제시하라.
- 더 단순한 접근이 있으면 말하라. 필요하면 반대 의견을 내라.
- 불명확하면 멈추고, 무엇이 헷갈리는지 이름 붙여 질문하라.

### 2. Simplicity First

문제를 푸는 최소 코드. 추측성 구현 금지.

- 요청 이상의 기능 금지. 단일 사용 코드에 추상화 금지.
- 요청 안 한 "유연성"/"설정 가능성" 금지. 불가능한 시나리오용 에러 처리 금지.
- 200줄을 짰는데 50줄로 될 것 같으면 다시 써라.
- "시니어 엔지니어가 과설계라 할까?" — 그렇다면 단순화하라.

### 3. Surgical Changes

건드려야 할 것만 건드려라. 네가 만든 것만 치워라.

- 인접 코드/주석/포맷을 "개선"하지 마라. 안 깨진 걸 리팩터링하지 마라.
- 다르게 하고 싶어도 기존 스타일에 맞춰라.
- 무관한 데드코드는 발견하면 언급만 하고 지우지 마라.
- 네 변경이 만든 고아(import/변수/함수)만 제거하라. 기존 데드코드는 요청 없이 지우지 마라.
- 테스트: 변경된 모든 줄이 사용자 요청으로 직접 추적되어야 한다.

### 4. Goal-Driven Execution

성공 기준을 정의하고 검증될 때까지 반복하라.

- "검증 추가" → "잘못된 입력 테스트를 쓰고 통과시켜라"
- "버그 수정" → "재현 테스트를 쓰고 통과시켜라"
- "X 리팩터" → "전후로 테스트가 통과하는지 보장하라"
- 다단계 작업은 `1.[단계]→검증:[체크]` 형식으로 짧은 계획을 밝혀라.

### 5. No Closing Colons (한국어 출력)

한국어 문장은 콜론이 아니라 마침표로 끝낸다.

- 다음 줄이 목록/예시여도 문장을 `:`로 끝내지 마라.
- 영어 문서 습관이 한국어에 새는 콜론을 잡아라.
- 모든 한국어 종결부는 `.`, `?`, `!` — 콜론 금지. (코드/키값/라벨 안의 콜론은 허용)

### 6. File Header Comments in Korean

모든 새 소스 파일 첫 줄: 역할을 밝히는 한 줄 한국어 주석.

- TS/JS: `// 사용자 인증 상태를 관리하는 Context Provider`
- Python: `# KIS API 호출을 비동기로 래핑하는 클라이언트`
- SQL: `-- 일별 집계 결과를 저장하는 머티리얼라이즈드 뷰`
- 지시자(`'use client'`, `'use server'`, shebang) 바로 아래 배치. 설정 파일은 제외.
- 이유: 에이전트는 파일을 선택적으로 읽는다. 한 줄 한국어 헤더가 즉각적 컨텍스트를 준다.

### 7. Plan + Checklist + Context Notes

비자명 작업 전 세 산출물을 만든다. 없이 코딩 시작 금지.

- **Plan** — 무엇을 왜 만드는가.
- **Checklist** (`checklist.md`) — 체크박스 작업 목록. 진행하며 체크.
- **Context Notes** (`context-notes.md`) — 작업 중 내린 결정과 근거. 계속 추가.
- 사용자가 계획만 주고 코딩을 시키면 멈추고 물어라. "체크리스트와 컨텍스트 노트를 먼저 만들까요?"

### 8. Run Tests Before Marking Complete

코드를 건드렸으면 "완료" 전에 테스트를 돌려라.

- `npm test`, `pytest`, `cargo test` 등 프로젝트가 쓰는 걸 돌려라.
- 통과하면 결과 보고, 실패하면 고치고 재실행.
- 테스트 셋업이 없으면 최소한 빌드/컴파일을 확인하라.
- "끝/완료/다 됐어" 신호 전에 선제적으로 돌려라. LLM이 가장 자주 건너뛰는 단계다.

### 9. Semantic Commits

하나의 논리 변경이 끝나면 커밋하라. 사용자 요청을 기다리지 마라.

- 테스트: "이 커밋을 한 문장으로 설명 가능?" 가능하면 커밋, 아니면 분리.
- 좋음: "auth 미들웨어 추가". 나쁨: "auth 추가하고 UI도 고치고 버그도 수정"(3개로 분리).
- 20개 무관 편집을 쌓아 개별 롤백 능력을 잃지 마라. 커밋을 위한 커밋 금지.

### 10. Read Errors, Don't Guess

실제 에러/로그 줄을 읽어라. 기억으로 패턴매칭하지 마라.

- 전체 에러 메시지와 스택 트레이스를 읽어라. 가정이 아닌 실제 로그를 확인하라.
- 원인 확인 전에 "흔한 수정"을 적용하지 마라.
- 불명확하면 print/log로 상태를 확인한 뒤 고쳐라.
- "테스트 실행" 다음으로 LLM이 가장 자주 건너뛰는 단계다. 키워드로 추측한 최근-패턴 수정이 한 줄 버그를 세 파일 리팩터로 만든다.

## 코딩 스타일 (세부)

### 불변성 (CRITICAL)

항상 새 객체를 만들고, 기존 객체를 절대 변형하지 마라. 숨은 부작용을 막고 디버깅과 안전한 동시성을 가능케 한다.

### 파일 구성

작은 파일 다수 > 큰 파일 소수.

- 높은 응집도, 낮은 결합도
- 200-400줄이 보통, 최대 800줄
- 큰 모듈에서 유틸리티를 추출
- 타입이 아니라 기능/도메인으로 조직

### 에러 처리

- 모든 레벨에서 명시적으로 처리. UI 대면 코드엔 사용자 친화적 메시지.
- 서버 측엔 상세 컨텍스트 로깅. 에러를 조용히 삼키지 마라.

### 입력 검증

시스템 경계에서 항상 검증.

- 처리 전 모든 사용자 입력 검증. 가능하면 스키마 기반.
- 명확한 메시지로 빨리 실패. 외부 데이터(API 응답, 입력, 파일)를 믿지 마라.

### 네이밍 & 구조 세부

- React 함수 컴포넌트는 TypeScript + 2칸 들여쓰기. 컴포넌트 `PascalCase`, 커스텀 훅 `useCamelCase`, 헬퍼 모듈 `camelCase.ts`.
- Tailwind 유틸리티 클래스 우선, 별도 CSS는 불가피할 때만.
- Supabase 클라이언트는 `src/lib/*.ts`, DTO는 `src/types/`, 환경 변수는 `SCREAMING_SNAKE_CASE`(`.env.example` 기준).
- `tsconfig.json`의 `@/*` 경로 별칭을 적극 활용한다.

### 코드 품질 체크리스트

- [ ] 가독성 있고 이름이 명확한가
- [ ] 함수가 작은가 (<50줄)
- [ ] 파일이 집중적인가 (<800줄)
- [ ] 깊은 중첩이 없는가 (>4레벨)
- [ ] 적절한 에러 처리
- [ ] 하드코딩 값 없음 (상수/설정 사용)
- [ ] 변형 없음 (불변 패턴 사용)

## 테스트 요구사항

- **최소 커버리지 80%.** 단위/통합/E2E 모두 요구.
- **TDD**: RED(테스트 먼저·실패 확인) → GREEN(최소 구현·통과) → REFACTOR → 커버리지 검증.
- 현재 SafeSys는 자동화 테스트 프레임워크가 없다. 린트·타입체크·수동 시나리오 검증이 필수다. [environment.md](./environment.md)의 검증 명령 참조.

## 계획서 (Plans)

계획서 작성 요청 시 `plans/`에 마크다운으로 작성한다.

- **저장 위치**: `plans/`
- **파일명 형식**: `YYYYMMDD_주제.md` (예: `20260323_인증시스템개선.md`)
- **수정/업데이트 시**: 파일명의 날짜 부분을 수정일로 변경

## 커밋 & PR

- **커밋 메시지**: `<type>: <description>` — type은 feat, fix, refactor, docs, test, chore, perf, ci. 명령형, 하나의 논리 단위.
- **PR**: 전체 커밋 히스토리 분석 → `git diff [base]...HEAD`로 전체 변경 확인 → 요약·테스트 플랜 작성 → 신규 브랜치는 `-u`로 푸시.
